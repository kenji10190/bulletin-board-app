# 技術選定の理由

データベース連携掲示板アプリで採用した主要技術について、選定の理由と移行の経緯をまとめています。

## バックエンド: Node.js + Express

Node.js を採用した理由は主に2点です。フロントエンド（Alpine.js）と言語を統一でき、文脈の切り替えコストを抑えられること。
そして標準モジュールのみで HTTP サーバーを構築できるランタイムであることです。

学習にあたっては、フレームワークの内部を理解しないまま使うことを避けるため、まず素の `http` モジュールから着手しました。
`req.url` によるルーティング、`res.statusCode` / `res.setHeader` の手動設定、`fs.readFile` による静的配信を自前で実装し、
その過程で `IncomingMessage` / `ServerResponse` がリクエストごとに生成される仕組みを公式ドキュメントで確認しています。

その上で Express へ移行しました。
素の Node.js ではルーティングが switch 文で肥大化し、共通処理やエラーハンドリングを都度書く必要があることを実装を通して体感していたため、
Express が何を抽象化するために存在するのかを理解した上で導入できました。

## データベース: PostgreSQL + Prisma

当初は学習用に SQLite を使用していましたが、Render へデプロイした際、再デプロイのたびに GitHub からソースを取得し直す挙動により、
ファイルベースの SQLite ではデータが揮発する問題に直面しました。データの永続化には外部のマネージドデータベースが必要と判断し、
無料枠で利用できる Supabase の PostgreSQL へ移行しています。

ORM には Prisma を採用しました。学習中に生 SQL でユーザー入力を文字列連結する書き方が
SQL インジェクションの温床になることを認識し、プレースホルダーによる対策に加えて、
安全な書き方を構造的に強制できる点で ORM の利点は大きいと判断したためです。
Prisma は SQLite / PostgreSQL の双方に対応しており、
DB 移行時もスキーマ定義の変更のみでデータアクセス層をほぼ書き換えずに済んだことも、結果的に大きな利点でした。

データモデルの観点でも、ユーザーに投稿が帰属し、各投稿が複数の属性を持つ構造で、
かつデータの整合性が求められる掲示板というアプリケーションには、NoSQL よりリレーショナルデータベースが適していると考えました。
